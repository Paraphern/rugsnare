### Кандидат №2 — канарейка контрактов (ядро этого брифа)

**Боль (подтверждена в окне):** апгрейд MCP-сервера (часто автоматический, через `npx -y`/`@next`/auto-update десктопа) молча меняет схему или семантику инструмента — агент тихо деградирует. Пиннинг отвечает «что изменилось», но не «можно ли обновляться».
Свидетельства: «That silent schema drift is nightmare fuel» — r/mcp, 09.09.2026; кластер июльских поломок: modelcontextprotocol/servers#4545 и claude-code#80094 (22.07.2026), azure-devops-mcp#1448 (23.07.2026), Zed#60474 (06.07.2026).
**Решение:** `rugsnare canary` — прокси пассивно пишет трассировки реальных tool-вызовов; при выходе новой версии сервера CI прогоняет записанный корпус против старой и новой версий, диффит `tools/list` + схемы + ответы, классифицирует изменения (breaking / cosmetic / semantic) и выносит вердикт «обновляйся / зафикси эти N вызовов». «Renovate для MCP-контрактов».
**Занятость:** RugSnare — пиннинг (только факт изменения); Pact — универсальные контракт-тесты, писать руками; поведенческой канарейки нет ни у кого. Оценка A (1–3 человека, 4–8 недель).
**Синергия:** drift-feed из «детектора изменений» превращается в публичный актив «какие апдейты реально ломают использование» — этого нет ни у Snyk, ни у Cisco.

### Кандидат №5 — подписанные квитанции (комплаенс)

**Боль:** логи сервис-аккаунтов не годятся как аудиторское доказательство действий агента (EU AI Act ст. 12 — применяется с 02.08.2026; IETF draft-sharif-agent-audit-trail-06 обновлён 29.09.2026). Свидетельства: r/grc 08.09.2026 и 28.09.2026 («weeks spent proving which agent version called which API…»).
**Решение:** Ed25519 hash-chain подпись каждой записи существующего per-call audit log → tamper-evident журнал; `rugsnare receipts verify`; экспорт «досье» (markdown/JSON) аудитору. Осторожно с форматом: следить за IETF-дрafтом, не изобретать своё, где он есть.

### Кандидат №11 — матрица клиентов (второй продукт)

**Боль:** один сервер по-разному работает в 9+ клиентах (транспорты, OAuth-заголовки, резолв окружения); «100% tool-call failure on Claude Desktop Windows» при работе в других клиентах (servers#4545, 22.07.2026).
**Решение:** GitHub Action/SaaS для авторов серверов: ферма подключает сервер к клиентам на нескольких ОС, smoke-сценарии (connect / auth / tools/list / вызов), бейдж «verified 8/9 clients». Инфра-риск: GUI-клиенты (Claude Desktop на Windows headless) — самая дорогая часть; возможно начать с CLI-клиентов (Claude Code, Codex CLI, Zed).

### Рекомендуемая последовательность

1. `rugsnare canary` — замыкает петлю «пиннинг → дифф → безопасное обновление», апгрейдит drift-feed.
2. Подписанные receipts — командная/комплаенс-фича поверх существующего лога.
3. mcp-matrix — второй продукт для стороны авторов (когда появятся ресурсы).
Не делать всё сразу: каждое расширение после первого должно опираться на уже написанное (прокси, пины, фид), иначе это четыре несвязанные ставки.

## Часть 2. Промт реализации (для сессии, где строим)

```
Ты — разработчик RugSnare (репозиторий C:\GlobalWork). Строй строго по фазам,
после каждой — коммит и стоп-точка. Ограничения проекта неприкосновенны:
zero npm-зависимостей в product/, Node ≥ 18, никакой телеметрии, локальные
хранилища, Apache-2.0, подписанные релизы (SECURITY.md), он-чейн ReleaseLog.

ФАЗА A — rugsnare canary (MVP, без LLM):
1. Формат корпуса: записи перехваченных вызовов (tool name, args, ответ/ошибка,
   версия сервера, таймстамп) в .rugsnare/canary/ — JSONL, локально. Расширь
   пер-call лог живого прокси, если его схемы не хватает.
2. rugsnare canary record — запись корпуса через существующий прокси.
3. rugsnare canary replay --against <версия|путь> — поднимает старую и новую
   версии сервера, прогоняет корпус, диффит: tools/list (это уже умеет diff),
   ответы (статус/структура/изменённые поля), ошибки.
4. Классификация без LLM: детерминированные правила (breaking: схема изменилась,
   required-параметр добавлен, enum сузился, ответ сменил тип, вызов упал;
   cosmetic: переименование описания, порядок полей). Выход: отчёт + exit code
   для CI. LLM-классификация — отдельный опциональный флаг позже (внешний вызов
   = отход от zero-deps, решение задокументировать).
5. GH Action: canary-job в существующий action/ + пример workflow.
6. Интеграция с drift-feed: при детекте смены контракта популярного сервера —
   прогон публичного корпуса (если есть разрешение) и публикация вердикта
   «апдейт ломает N паттернов вызовов» в фид.
7. Repro-скрипт (в repro/): на базе существующего field-test (server-filesystem
   2026.8.31 vs 2026.1.14) — канарейка обязана поймать реальное поведение-
   расхождение, не только описание.
Критерий приёмки: bash repro/canary.sh ловит подмену версии и печатает
verdict с exit 1; на одинаковых версиях — exit 0 без ложных срабатываний.

ФАЗА B — receipts:
1. Подпись записей audit log: Ed25519, hash-chain (каждая запись ссылается на
   хэш предыдущей), ключ — локальный, ротация по образцу SECURITY.md.
2. rugsnare receipts verify --from <файл> — проверка цепочки, вывод таймлайна
   «что агент вызывал, с какими аргументами, когда».
3. rugsnare receipts export --format dossier — человекочитаемый экспорт для
   аудитора (markdown + JSON). Названия полей максимально близко к
   IETF draft-sharif-agent-audit-trail (не изобретать своё).
Критерий приёмки: подделка одной записи в середине журнала детектится verify.

ФАЗА C — mcp-matrix (отдельный репозиторий/продукт, отдельное решение):
оформи как proposal-doc в этом репо (аудитория, фермa CLI-клиентов первой
очередью, бейдж), не начинай код без отдельной команды.
```

## Часть 3. Промт для агента-разработчика RugSnare (аудит применимости)

```
Ты — агент-разработчик проекта RugSnare (репозиторий C:\GlobalWork). Задача —
не кодить, а провести технический аудит применимости расширений, описанных
в файле rugsnare-extensions.md (лежит в корне репо; прочитай его целиком,
включая свидетельства и источники).

ПОРЯДОК РАБОТЫ:
1. Сначала изучи фактическое состояние кода, НЕ доверяя брифу на слово:
   - product/src: что реально пишет живой прокси (rugsnare run) в per-call
     audit log — какие поля, хватает ли их для реплея вызова (аргументы?
     полные ответы? версии сервера?);
   - .rugsnare/pins.json и формат pins — что уже пиннится;
   - drift-feed/ — что собирается, в каком формате, есть ли корпус вызовов;
   - repro/ и corpus/ — что годится как тестовая база для канарейки;
   - action/ — как устроен существующий CI-гейт.
   Каждое утверждение о коде подтверждай путём к файлу (и строке, если важно).
2. Для каждого кандидата из Части 1 брифа (№2 canary, №5 receipts, №3 loop-
   сигнал, №11 matrix, №1 verified-tool) вынеси вердикт:
   - ПРИМЕНИМО / ПРИМЕНИМО С ОГОВОРКАМИ / НЕ ПРИМЕНИМО — и почему, с опорой
     на код, а не на бриф;
   - каких блоков не хватает в текущем коде (точный список: схема лога, записи
     ответов, entorno-переменные, механизм снапшота версии);
   - оценка усилия в PR'ах и главный риск (включая конфликты с trust-моделью:
     zero-deps, no telemetry; для canary — допустим ли опциональный внешний
     LLM-вызов; для matrix — инфра-стоимость GUI-клиентов);
   - каннибализация/размытие: не ломает ли расширение текущее позиционирование
     «integrity-слой контрактов»;
   - первый шажок размером с один PR (конкретно: файлы, команда, тест).
3. Проверь два факта брифа по внешним источникам (веб-поиск): статус IETF
   draft-sharif-agent-audit-trail и жива ли ссылка на r/mcp-тред про schema
   drift. Если что-то не подтверждается — пометь в вердикте.
4. Результат оформи файлом extensions-verdict.md в корне репозитория:
   - таблица «кандидат → вердикт → усилие → риск → первый PR»;
   - разбор каждого кандидата (кратко, с путями к коду);
   - итоговая рекомендация: порядок внедрения и что отложить;
   - раздел «расхождения с брифом» — все места, где код оказался не тем,
     что предполагал бриф.
5. Не модифицируй продуктовый код. Только чтение, поиск и один новый файл
   extensions-verdict.md.

Будь честным: если прокси не пишет ответы вызовов — канарейка не может
работать на текущем логе, и это должно быть главным выводом, а не сноской.
```
