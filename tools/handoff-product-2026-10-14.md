## ЗАДАЧА 1 (главная): skills `path` - абсолютные пути пережили релиз

ЧТО СЛОМАНО: в pins.json поле skills.<key>.path пишется машинно-абсолютным путём.
Живой пример с вашей публичной 1.4.0 (вчера, rugsnare@1.4.0 skills scan):
  "path": "C:\\tmp\\skills14\\sp7\\.opencode\\INSTALL.md"   <-- абсолютный, течёт
  "relative": "INSTALL.md"                                   <-- рядом уже есть правильный

СПЕК-ТРЕБОВАНИЕ (нарушено): PIN-SPEC §2, storage rules, пункт skills, маркирован (v1.1):
"path MUST be stored relative to the skill root - the 1.3.0 writer emits machine-absolute
paths, which breaks §7 byte-stability across machines and leaks local layout; fixed in the
v1.1 writer." История изменений v1.1 говорит "Implementation lands in rugsnare 1.4.0" -
для этого пункта НЕ случилось.

ПОЧЕМУ ЭТО ВАЖНО (три причины):
1. Байт-стабильность (§7) - публичное обещание из autogen#7353: одно и то же дерево скиллов,
   отсканированное из двух каталогов/машин, даёт РАЗНЫЕ байты пина -> сторонние хэши
   (receipt-композиция §7.1, snyk-коллаборация) невоспроизводимы для skills.
2. Утечка локальной структуры: в ОПУБЛИКОВАННОМ каталоге audits/drift-watch/pins/ три
   skills-снимка несут наши локальные пути (включая C:\GlobalWork\...).
3. Блокирует мою задачу: каталог skills-снимков не перегенерируется, пока путь абсолютный
   (перегенерация воспроизведёт утечку с новой меткой версии).

ЧТО СДЕЛАТЬ (выберите один вариант и синхронизируйте спек со мной):
- ВАРИАНТ А (проще): path = то же значение, что relative (относительный путь от корня
  скилл-скана). Поле остаётся, совместимость полная.
- ВАРИАНТ Б: поле path удалить совсем, оставить relative (оно уже "the stable key
  component" по спеку). Чище, но это смена формы - тогда я правлю §2 и мы фиксируем
  в CHANGELOG, что 1.4.1 writer перестал эмитить path.
Рекомендуем А: нулевой риск формата, нулевая правка спека.

КРИТЕРИИ ПРИЁМКИ (прогоню сам, но перечислите в тестах):
1. skills scan любого дерева из ЛЮБОГО каталога -> в pins.json поле path без диска и без
   ведущего слэша (никаких "C:\\" и никакоого "/home/...").
2. Одно и то же дерево, отсканированное из двух разных checkout-каталогов -> байт-идентичные

3. Существующие тесты обновлены + новый тест на относительность path (как сделали с

4. CHANGELOG 1.4.1: одной строкой "skills pin path is now relative (PIN-SPEC §2)".

## ЗАДАЧА 2 (бумажная, 2 минуты): коллизия R-номеров

В вашем разборе P0-1 вы записали кандидата (scan --prune / предупреждение о "мёртвых
душах") как R35. В нашем общем журнале улучшений (tools/rugsnare-improvements-2026-10-11.md)
номера уже заняты:
- R35 = класс MIRRORED + канал вендор-аннотаций (урок currents#232 от twk3: "зеркалирование
  существующей бэкенд-валидации != новое ограничение"; операционное определение BREAKING
  уточнено: "ранее успешный вызов начинает падать")
- R36 = openapi-crosscheck: автоматическая MIRRORED-разметка по опубликованному OpenAPI-спеку
  вендора (машиночитаем, rugsnare может сверять constraint-добавления сам)
- R37 = ваш prune-кандидат (я перенумеровал у себя)
Просьба: в ваших внутренних записях переномеруйте prune-кандидат на R37 (или просто
учтите соответствие при кросс-ссылках), чтобы R35/R36 в наших сообщениях означали одно и то же.
