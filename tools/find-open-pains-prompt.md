# Промт: поиск УЖЕ ОТКРЫТЫХ болей под rugsnare (спрос-пулл, не холодный аутрич)

Статус: метод проверен 2026-10-07..10 на Microsoft azure-devops, Chrome devtools, DeepSeek RFC, cline. Промт самодостаточен, можно вставлять в свежую сессию без контекста.

---

## Задача

Найти на GitHub существующие открытые issue/discussion, где человек УЖЕ жалуется на то, что ловит rugsnare: MCP-инструмент изменился, исчез, переименовался, поменял схему после обновления сервера. Не создавать спрос, а находить его. Мы приносим чеки (точная граница версии + воспроизводимый дифф), rugsnare упоминаем одной строкой в хвосте как "чем поймал".

## Философия (почему это работает)

Владелец issue не обязан нам ничего: у него боль, у нас факты. Коммент полезен, если отвечает на его вопрос ("когда это сломалось", "куда пропало", "почему другое") с точностью до версии. Худший вариант - прийти в чужой тред со ссылкой на инструмент без фактов. Это спам, он сжигает репутацию.

## Путь A: от дрейфт-карты к боли (так нашли Microsoft и Chrome)

Использовать, когда у нас уже есть аудит пакета (rugsnare history или недельный трекер): карта "какой инструмент в какой версии менялся".

1. Определить репозиторий вендора: `npm view <package> repository.url` (бывает, что официального репо нет - тогда путь закрыт, смотри путь B).
2. Искать в их трекере жалобы, совпадающие с нашими находками. Сначала по ИМЕНАМ изменённых инструментов (самый высокий сигнал):
   - `gh search issues "<имя_инструмента>" --repo <vendor/repo> --state open --sort created`
   - затем по форме жалобы: `gh search issues "broke OR changed OR missing OR renamed" --repo <vendor/repo> is:issue --sort created`
3. Кросс-референс: жалоба открыта И упоминает инструмент/версию из нашей карты. Тогда у нас есть то, чего нет у автора: точная версия, где поведение изменилось.
4. Проверить эмпирически перед ответом: прогнать обе версии пакета (старую и новую) и снять дифф. НИКОГДА не утверждать дрейфт по памяти аудита - только свежий прогон (урок chrome-devtools: "6 находок" при проверке оказались 0 параметрических, корректировку пришлось постить отдельно).
5. Формула комментария: (а) точная граница версии X.Y.Z -> X.A.B, (б) что именно изменилось в этом инструменте, (в) репро-команды, (г) rugsnare одной строкой в конце.

Примеры, где сработало:
- microsoft/azure-devops-mcp #1682: жалоба на `testplan_show_test_results_from_build_id` - инструмент из нашего BREAKING-списка 2.5.0 -> 2.10.0. Наша карта переименований объясняла их симптом.
- ChromeDevTools/chrome-devtools-mcp #2917: вопрос "куда пропало предупреждение" - наши посканальные чек-риды показали, в какой конкретно версии оно исчезло.

## Путь B: от поиска жалоб к целям (так нашли DeepSeek RFC #12356 и cline #14924)

Ежедневный прогон по всему GitHub. Сортировка строго по created (updated захватывает бото-борды и борды зависимостей):

```
gh search issues "<запрос>" --sort created --limit 20 --json repository,title,url,state,createdAt,updatedAt
```

Рабочие запросы (проверены 2026-10-08, запускать все):

- `mcp broke in:title`
- `mcp stopped working in:title`
- `mcp tools changed in:title`
- `allowed-tools`
- `mcp schema changed breaking`
- `claude skills mcp update broke`

Чтобы ограничить свежесть, добавлять квалифаер `created:>2026-10-01` (подставлять дату недели). Фраза в кавычках внутри запроса = literal phrase; слова без кавычек ищутся раздельно; OR только заглавными.

Вариант по конкретному вендору: те же запросы с `--repo microsoft` и т.п., когда хотим зацепиться с конкретной экосистемой.

## Пороги фильтра (все три обязательны, иначе пропуск)

1. Жалоба живая: state = open, updatedAt за последние ~2 недели. Год молчания = аудитория ушла.
2. У автора реальная боль: не "как настроить", а "сломалось / изменилось / исчезло / молча добавилось". Вопросы конфигурации не наши.
3. Наш метод даёт факты: мы можем прогнать пакет и дать точный ответ (версия, дифф, репро). Если к теме rugsnare ни при чём - пропуск, какая бы популярная тема ни была.

Приоритет повышается, если: RFC/design-discussion про пиннинг или approval (нам приглашённая площадка), 0 комментариев при живом авторе (мы первые с данными), вендор из топа по установкам.

## Чек-лист перед КАЖДЫМ постом (обязателен)

1. `gh issue view <n> --repo <r> --json state,stateReason,closedAt` - state closed означает НЕ постить (урок azure-devops #1448: запостили в закрытую с июля, минус доверие).
2. Прочитать тело issue и ВСЕ комментарии: закрытые треды часто ссылаются на дубль/PR/discussion - идти туда.
3. Discussions: `gh api repos/<r> --jq .has_discussions` - исследовательский контент лучше в discussion (не закрывается как баг).
4. Свежий прогон пакета сделан сегодня, чеки в кармане.
5. Не долбить канал, где на наш прошлый контент 0 реакций и 0 ответов.
6. Один репозиторий в день максимум для исходящих. Не постить одно и то же в несколько мест подряд.
7. Ни одного длинного тире (—) в тексте. Всегда короткое (-).

## Правило самопроверки тезисов (добавлено 2026-10-13, уроки github-mcp #3466 и Anthropic-кластера)

ПЕРЕД постингом каждое утверждение драфта сверяется на двух сторонах. Это правило №0 по силе
после "не постить в закрытое": ошибка в чужом треде дороже пропущенного треда.

А. Сверка ПРОТИВ ИХ стороны:
- читаю их КОД, не только тело issue (урок LiteLLM: их _drifted = dict-compare -> совет про
  сортировку ключей оказался неприменим; урок WSO2: patch inspection.go показал schema-walker -
  и признание их модели усилило вход);
- проверяю формулировки на абсолюты ("ничего не сообщает", "всегда") - смягчать до проверяемого
  ("as far as I can tell", "в обоих тегах подтверждено");
- проверяю, что уже сказали другие в треде (count по ключевым словам: если тезис поднят - не
  выдавать за отсутствующий, урок #16345: "mostly absent" после count=1/31).

Б. Сверка ПРОТИВ НАШЕЙ стороны (grep по product/src перед каждым "мы умеем"):
- заявленная фича существует в коде? (урок Anthropic #93318: заявил "pin by plugin namespace" -
  а SKILL_LOCATIONS не покрывает claude-плагин-каталоги; заявил "детект смены scope" - а вердикты
  только UNCHANGED/DRIFT/NEW/REMOVED, переезд = пара REMOVED+NEW);
- заявленный статус ("уже в дереве" vs "на этой неделе" vs "в npm") сверять с деревом и npm;
  публичное обещание срока = риск (урок R27: собирался писать "this week", проверка показала
  "уже в дереве" - правда стала сильнее без обещаний);
- приписывать себе только выстраданное (урок LiteLLM: outputSchema мы сами не пиним - подавали
  как "честную общую дыру", это сильнее, чем менторский тон).

В. Формат проверки: таблица "утверждение -> как проверено -> вердикт (правда/полуправда/ложь)".
Каждое "полуправда" и "ложь" обязаны изменить драфт. Таблица показывается пользователю вместе
с драфтом. Примеры-эталоны: проверка AAtomless-поправок (3/3 подтверждены на тегах), сверка
Anthropic-трёх (поймали 3 неточности до постинга).

## Анти-паттерны

- Прийти без фактов: ссылка на инструмент вместо ответа на вопрос автора.
- Утверждать дрейфт без свежего прогона обеих версий.
- Постить в закрытое / год молчавшее.
- Переоткрывать свою боль в чужом треде ("а ещё у вас X сломан") - для этого отдельный issue.
- Дубли (учок Apify #1514/#1515: таймаут создания не означает провал - проверять список issue после каждой операции).

## Выход промта

Таблица кандидатов: репо, номер, ссылка, автор, дата, суть боли, совпадение с нашей картой (или путь B), вердикт (постим / проверяем пакет / пропуск), причина. До постинга показать пользователю драфт комментария.
