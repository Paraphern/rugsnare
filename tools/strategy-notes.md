# Стратегические заметки RugSnare (открыто 2026-10-08)

Живой документ. Здесь - соображения уровня «куда движемся», не факты диалогов (те - в github-interactions-log.md) и не правила аутрича (те - в github-outreach-notes.md).

## 1. Открытая спецификация пинов («общий язык отпечатков»)

**Идея:** оформить формат `.rugsnare/pins.json` как открытую спецификацию (JSON Schema + документация полей: per-tool hash / schemaHash / proseHash / description, классы изменений DRIFT|NEW|GONE с типами BREAKING/COSMETIC/ANNOTATION).

**Зачем:** клиенты, встраивающие нативный пиннинг (DeepSeek-Reasonix RFC #12356 - первый реальный кандидат, Go), смогут экспортировать/импортировать базовые линии, совместимые с нашими. Тогда клиент ловит дрейфт на своей стороне, наш CI - на своей, а отпечатки совпадают. Мы становимся не «ещё одним инструментом», а **языком, на котором экосистема говорит о дрейфте**.

**Момент для хода:** когда RFC #12356 получит приоритет и у автора встанет вопрос формата его baseline-хранилища (у него - per-user JSON в MCPStateDir). Не предлагать раньше: сейчас его формат - его внутреннее решение, наш пуш будет выглядеть как захват.

**Что подготовить заранее (тихо):** JSON Schema на pins.json v1, короткий README раздел "Pin format spec", пример межинструментной совместимости (взять базовую линию из rugsnare, сверить внешним скриптом). Это также дисциплинирует нас самих: формат станет контрактом - менять придётся версионированно.

## 2. Ниша при натурализации пиннинга в клиентах

**Факт:** RFC #12356 - «rugsnare, вшитый в клиент» (Go, ~5 дней работы). Если тренд пойдёт - клиент-нативный пиннинг станет нормой.

**Наша позиция (дополнение, не конкуренция):**
- **CI / командный слой** - его baseline per-machine без синка; Якуб прямо признал: «для командного ревью ваши закоммиченные пины в CI - лучшая модель» (лог, 2026-10-08)
- **Мультиклиентность** - один пин на все клиенты пользователя (Claude Code, Cline, Cursor...)
- **Исследовательский слой** - полевые аудиты, weekly-трекер, corpus, данные которые цитируют (уже: RFC + KyttoMCP)
- **Клиенты без нативного пиннинга** - большинство ещё долго

**Вывод:** каждый новый клиент с нативным пиннингом - валидация угрозы и наш соавтор по формату, не конкурент по нише.

## 3. Градирование серьёзности внутри BREAKING (идея Якуба)

**СТАТУС: РЕАЛИЗОВАНО продукт-чатом 2026-10-08** - schemaNotationDiff() в pins.js, правило «параметры изменились → BREAKING; байты схемы изменились, параметры нет → NOTATION», 300/300 тестов. Живая валидация chrome 1.8.0→1.10.1: 0 BREAKING + 30 NOTATION.

**Уточнение от верификации стратега (2026-10-08, 23:37):** «ноль параметров» подтверждено; но остаток НЕ однороден: (а) SDK-сгенерированные границы integer ±9007199254740991 на timeout/pageSize/pageIdx - сериализационный артефакт, чистая нотация; (б) правки текстов description внутри параметров; (в) одно ослабление валидации - fill_form.elements потерял additionalProperties:false на items (расширение множества принимаемого - формально schema-семантика, направление мягкое). Открытый мини-вопрос продукт-чату: считать ли (в) NOTATION-with-note или отдельным micro-классом. Для RFC-коррективы формулировка: «0 parameter-level; residue = SDK bounds + prose + one loosened validation».

**Ответ Якубу (план 2026-10-09):** «ваш пункт уже меняет продукт» + числа 0/30 + упоминание, что его градирование натолкнуло на разбор остатка.

## 4. Product идеи из диалогов (backlog)

- Response-shape assertions - «следующий слой» (признан публично в discussion #1): пинить форму ОТВЕТОВ инструментов, не только контрактов. Закрывает слепоту: контракт тот же, а данные под ним другие (кейс azure #1682 - описание обещает поля, ответ их не несёт). **Живое подтверждение класса 2026-10-09: DavidS-msft зафиксировал, что поля терялись при неизменном контракте, и PR #1684 чинит именно response-слой.**
- **Remote-channel drift - теперь с именным кейсом (2026-10-09):** azure-devops-mcp: локальный npm-канал (2.10.0, поля отсутствуют) и хостимый streamable-HTTP-канал (поля на месте) версионируются раздельно; remote движется вне ритма npm-релизов. Пиннинг только npm не видит remote-изменений. Задел: (а) строка в PIN-SPEC о per-channel пинах; (б) будущая фича - одновременный пин обоих каналов одного продукта; (в) контент-сюжет «один продукт - два контракта».
- Спрос-пулл канал работает: 3 находки на первый прогон. Поддерживать ежедневный прогон запросов (github-outreach-notes.md).
- «Аудит по жалобе» (модель datadog-copilot#2087): пользователь жалуется «сервер сломался» - мы эмпирически проверяем дрейфт пакета и приходим с фактом. Потенциально формат услуги/контента.
