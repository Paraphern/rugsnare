# Бриф для передачи: стратегия RugSnare (контекст → реализация → результат)

Дата: 2026-10-08. Документ самодостаточен: логика прослеживается без доступа к исходной переписке. Все файлы - в репозитории C:\GlobalWork (github.com/Paraphern/rugsnare, npm: rugsnare).

## 0. Что такое RugSnare (30 секунд)

CLI-инструмент (Node ≥18, ноль зависимостей, Apache-2.0), решающий проблему MCP-экосистемы: **описания инструментов MCP - это инструкции, которые агент читает и выполняет, но они могут молча измениться после одобрения сервера**. RugSnare пиннит контракт каждого инструмента при одобрении (`scan`), сравнивает при каждом обновлении (`diff`), ломает сборку при дрейфте (exit 1), имеет `approve`, живой stdio/HTTP-прокси, CI-гейт, on-chain верификацию релизов. Формат хранилища: `.rugsnare/pins.json` - per-tool три хэша (полный контракт, канонизированная схема, проза) + классы изменений (DRIFT с типами BREAKING/COSMETIC, NEW, GONE).

## 1. Откуда взялся запрос (хронология триггеров)

1. **Полевой аудит (7 окт).** Мы прогнали rugsnare по топ-9 npm MCP-серверов: 218 тихих изменений контрактов (Microsoft azure-devops-mcp: 110, включая 75 удалённых инструментов минорными версиями; chrome-devtools-mcp: все 28 схем за 5 недель; и т.д.). Отчёт: `audits/npm-top-mcp-drift-2026-10.md`, еженедельный трекер `audits/WEEKLY.md` (CI, по понедельникам).
2. **RFC DeepSeek-Reasonix #12356 (8 окт).** Автор Go-клиента предложил ВСТРОИТЬ в клиент ровно нашу механику (пиннинг при одобрении, hold изменённых инструментов до явного accept), ссылаясь на кампанию Deadbugz (сервер менял метаданные после 3 вызовов). У его RFC был раздел «Unverified»: «частота легитимных изменений не измерена». Мы ответили первыми нашими измерениями (4/9 дрейфтнули; усталость одобрений концентрированная) + дизайн-уроками. Его ответ: «вобьём цифры и три пункта в RFC, аудит процитируем как внешний источник». То есть клиент-нативный пиннинг становится реальностью, и он строится на наших данных.
3. **Диалог с KyttoMCP (8 окт).** Автор MIT-десктоп-менеджера MCP (Contract Guard - та же функция) публично признал в нашем треде баг у себя (baseline перезаписывается каждым проходящим check'ом) и принял наш corpus как тест-фикстуры с атрибуцией. Заодно предложил идею: **градировать серьёзность внутри BREAKING** (смена диалекта $schema - ниже, чем смена параметров).

Итого триггер запроса: экосистема начала строить пиннинг нативно в клиентах; наши данные и артефакты стали конвертируемой валютой (нас цитируют, у нас берут корпус); встал вопрос - как из «одного из инструментов» стать инфраструктурным слоем.

## 2. Суть стратегии (5 пунктов, по приоритету)

### П1 (главный). Открытая спецификация пина («общий язык отпечатков»)
Оформить формат `.rugsnare/pins.json` как открытую спецификацию. Тогда клиенты с нативным пиннингом (первый кандидат - DeepSeek-Reasonix, его baseline - per-user JSON) смогут экспортировать/импортировать базовые линии, совместимые с нашими: клиент ловит дрейфт на своей стороне, наш CI - на своей, отпечатки совпадают. Мы становимся языком, а не инструментом.

### П2. Позиционирование при натурализации пиннинга
Нативный пиннинг в клиентах - не угроза, а валидация. Наши четыре опоры: (а) CI/команды (их baseline per-machine без синка - Якуб прямо признал наше превосходство там), (б) мультиклиентность (один пин на все клиенты), (в) исследовательский слой (аудиты, weekly-трекер, corpus), (г) большинство клиентов ещё долго без натива.

### П3 (с дедлайном!). Градирование BREAKING
Принять идею Якуба: разделить BREAKING на параметрический и диалектический (смена $schema-диалекта/формы additionalProperties - ниже смена параметров). Решить до ответа Якубу (план: 9 окт), тогда ответ = «ваш пункт уже меняет наш продукт».

### П4. Product-backlog из диалогов
- Response-shape assertions: пинить форму ОТВЕТОВ инструментов (контракт тот же, данные другие - кейс azure #1682: описание обещает поля, ответ их не несёт). Публично анонсировано в discussion #1 как «следующий слой».
- «Аудит по жалобе»: пользователь жалуется «сервер сломался» → мы эмпирически пин/диффим пакет → приходим с фактом (пилот: microsoft/copilot-intellij-feedback#2087, Datadog MCP).

### П5. Наблюдения для контента
Поиск GitHub-issues по updated забит ботобордами (агентские репо логируют сами в себя); reactions ≠ метрика (метрика - принятия артефактов).

## 3. Как реализовать

### П1 (спека пина) - шаги:
1. Извлечь реальную структуру pins.json (есть примеры: `C:\tmp\bigfish2\.rugsnare\pins.json` и в корусе тестов продукта `product/test/`) и формализовать: JSON Schema (draft 2020-12), поля: `version`, `servers.{name}.{cmd,pinnedAt,tools.{tool}.{hash,schemaHash,proseHash,description,schema?}}`, семантика канонизации (ключи отсортированы, порядок массивов значим, `$schema`-диалект сохраняется), классификация изменений.
2. Добавить в README раздел «Pin format (spec v1)» + отдельный файл `docs/PIN-SPEC.md`.
3. Тест совместимости: сторонний скрипт (без нашего кода) читает pins.json по спеке и сверяет два пина. Это доказывает открытость.
4. КРИТИЧНО - тайминг публикации: НЕ пушить спеку, пока RFC DeepSeek-Reasonix не получил приоритет и не упёрся в формат своего baseline-хранилища. Раньше - выглядит захватом. Триггер для публикации: правка RFC с нашими цифрами ИЛИ вопрос автора про формат. Подготовить сейчас тихо.
5. Цена вопроса для нас самих: формат становится контрактом → любые изменения pins.json только через версионирование поля `version`.

### П3 (градирование) - шаги:
1. В классификаторе диффа (продукт, `product/src/`) найти место классификации schemaHash-изменений.
2. Ввести подтипы: `BREAKING` (параметры: добавлен/удалён параметр, смена типа, required-изменения) и `NOTATION` (только $schema-диалект / additionalProperties-форма / порядок уже канонизирован). Старый класс COSMETIC (проза) без изменений.
3. Обновить тесты (в продукте их 247) + weekly-скрипт `audits/run-weekly-audit.mjs` не требует прав (читает счётчик).
4. Проверить на живом кейсе: chrome-devtools 1.8.0→1.10.1 должен дать 6 BREAKING + 22 NOTATION (сегодня - 28 BREAKING). Это и будет демо-доказательством в ответе Якубу.

### П4.1 (response-shape) - только дизайн-заметка, не раньше чем П1/П3 закрыты.
### П4.2 (аудит по жалобе) - пилот по готовности: datadog MCP (npm-пакет) pin/diff, результат в issue #2087 фактом.

## 4. Что нам это даст

- **П1** превращает rugsnare из «одного из» в инфраструктуру: если хотя бы один клиент примет совместимый формат, цепочка «клиент ↔ CI ↔ трекер» замыкается на нас; риск блокировки (vendor lock) отсутствует - формат открытый, выигрывает тот, кто его поддерживает лучше всех. Также дисциплинирует собственный формат.
- **П3** снимает главный аргумент критиков («шумит на миграциях»), даёт готовый ответ Якубу и публичное доказательство, что обратная связь меняет продукт.
- **П2** - рамка для всех коммуникаций: не конкурировать с клиентами, а поставлять им слой.
- **П4** - конвейер контента и потенциально формата услуги.
